## 🔒 Security

### 🔵 Low — Two dependency advisories still open
- **Where:** `package.json` (`shadcn`, `better-auth` → `drizzle-kit`)
- **Issue:** `pnpm audit --prod` (run today) reports 2. `braces` ≤3.0.3, high by the advisory's label, under `shadcn > fast-glob > micromatch`. `esbuild` ≤0.24.2, moderate, under `better-auth > drizzle-kit > @esbuild-kit/…`.
- **Why it matters:** Both sit in command-line tooling, not in code that answers web requests. I rate it Low for that reason. The "high" label is the advisory's, not mine.
- **Fix:** `pnpm update shadcn drizzle-kit better-auth` and re-run the audit. If `braces` is still flagged, move `shadcn` to `devDependencies`, since it is a CLI.

### 🔵 Low — Failed and denied sign-ins leave no trace
- **Where:** `src/lib/activity.ts:11`, `src/lib/auth.ts:44-47,78`
- **Issue:** The only auth events written to the activity log are `member.joined` and `member.left`. A run of wrong passwords, or a refused sign-up, is not recorded anywhere the owner can see.
- **Why it matters:** The rate limit slows guessing but nobody would know it was happening.
- **Fix:** Log failed sign-ins from a Better Auth `hooks.after` on `/sign-in/email`, with the email tried and no password.

### 🔵 Low — No length or range limits on order text and money on the server
- **Where:** `src/lib/orders.ts:13-25`
- **Issue:** `customerName`, `items`, `notes` and `deliveryAddress` have no `.max()`. `total` allows any number of digits, so `Math.round(Number(input.total) * 100)` (line 43) can exceed safe-integer range.
- **Why it matters:** Only signed-in staff can post, so this is a robustness issue, not an attack path. One pasted megabyte would slow the list pages, which read every row.
- **Fix:** Add `.max()` to the text fields (for example 200 for names, 2000 for items and notes) and cap `total` at a sensible figure.

### ⚪ Info — Content-Security-Policy only covers framing
- **Where:** `next.config.ts:9`
- **Issue:** The CSP header is just `frame-ancestors 'none'`, with no `script-src`. There is no HSTS header.
- **Why it matters:** Nothing here is wrong for a local app. Worth revisiting if it goes online, together with the https address (cookie flags depend on `BETTER_AUTH_URL`/`APP_URL` being https; the `.env` values were not printed in this audit).

### ⚪ Info — First visitor becomes the owner
- **Where:** `src/lib/auth.ts:59-60`, `src/app/(auth)/sign-up/page.tsx:21-30`
- **Issue:** While there are zero users, `/sign-up` is open to anyone who can reach the server, and the first account gets the owner role. The check is a count followed by an insert, so two sign-ups at the exact same moment on an empty database could both become owners.
- **Why it matters:** This is the stated design and harmless on a laptop. Create the owner account before the app is reachable by anyone else.

### ⚪ Info — Sign-up reveals whether an invitation is waiting
- **Where:** `src/app/(auth)/sign-up/page.tsx:33-55`, `src/lib/auth.ts:73-76`
- **Issue:** The public sign-up page shows a different message depending on whether any invitation is pending. The "Sign-up is closed" error on submit also tells a visitor their address was not invited.
- **Why it matters:** Tells an outsider almost nothing useful. Noted for completeness.

**Checked and clean:**
- **Injection and XSS:** no `dangerouslySetInnerHTML`, `innerHTML`, `eval`, `new Function`, `child_process`, or raw SQL built from input. The only `sql` template uses are constant defaults in `auth-schema.ts` and `select 1`. All queries go through Drizzle. Search text goes into `like()` as a parameter (`%` and `_` act as wildcards, harmless).
- **Secrets:** `.env` is git-ignored and not tracked (`git ls-files` shows none). No keys or tokens in tracked files. The System page reports set/not-set only.
- **Access control:** every page calls `requireUser`/`requireAdmin`; every server action and the export route call `requireUserAction`/`requireAdminAction`. There is no middleware, so each route guards itself, and all of them do. The `role` field has `input: false`, so a user cannot set their own role. Export returns only the caller's own orders.
- **Other:** no `target="_blank"` links, no `localStorage`/`sessionStorage`, no CDN scripts (fonts via `next/font`). The SQLite file is git-ignored.
- **Auth package `cn`:** `node_modules/cn` is the shadcn team's own package (repository `shadcn-ui/cn`), not a look-alike.

## 🧱 Code Quality

### Performance

#### 🔵 Low — "All orders" reads every row, and the order table has no indexes
- **Where:** `src/lib/orders.ts:74-92`, `drizzle/0000_glorious_joseph.sql` through `0003`
- **Issue:** `listOrders` has no `limit`. The status and date filters (`status`, `due_date`) have no index. Only the auth tables do.
- **Why it matters:** Invisible at a few hundred orders. After a few years of catering it becomes a slow, very long page.
- **Fix:** Add an index on `(status, due_date)` and page the list (for example 50 at a time).

### Bugs / Correctness

#### 🔵 Low — Server accepts impossible dates and times
- **Where:** `src/lib/orders.ts:15-16`, `src/lib/time.ts:45-50`
- **Issue:** The checks are format-only: `/^\d{4}-\d{2}-\d{2}$/` and `/^\d{2}:\d{2}$/`. `2026-02-31` and `99:99` both pass. `clockTime("99:99")` would show "3:99 am".
- **Why it matters:** The browser's date and time inputs stop this in normal use, so it needs a hand-made request. Staff can't reach it from the form.
- **Fix:** Validate the ranges, or parse with `Date.UTC` and compare back.

#### 🔵 Low — Changing the status of a missing order says nothing
- **Where:** `src/app/(app)/orders/actions.ts:62-67`, `src/lib/orders.ts:140-148`
- **Issue:** `setOrderStatus` returns `false` when the id does not exist, but `changeStatus` ignores it and redirects to `/`. `saveOrder` does report a missing order.
- **Why it matters:** If two people have the same order open and one order is gone, the other taps "Mark done" and nothing tells them it failed.
- **Fix:** Check the return value and show the same "That order no longer exists" message.

#### 🔵 Low — Status entries in the activity log don't say which order
- **Where:** `src/lib/orders.ts:147`; `src/app/(app)/settings/system/page.tsx:21-26`
- **Issue:** `order.done`, `order.cancelled` and `order.upcoming` are logged with `{ id }` only, so the System page shows "Marked an order done" with no customer name. Create and change entries do carry the name.
- **Fix:** Look up and log `customer` the same way `updateOrder` does.

#### ⚪ Info (Potential) — Database handle is created at module load with no reuse guard
- **Where:** `src/lib/db/index.ts:5`
- **Issue:** `new Database("./data/app.db")` runs whenever the module is evaluated. Under `next dev` hot reload, that can open extra handles on the same file. I did not observe a problem; this is the usual pattern worth guarding with a `globalThis` cache. The path is also relative to the working directory, so the app must be started from the project root.

### Tech debt & maintainability

#### 🔵 Low — No automated tests
- **Where:** `package.json` (no `test` script), no `*.test.*` files in the repo
- **Issue:** Logic that matters has no tests: the sign-up hook that decides who may create an account and with which role (`src/lib/auth.ts:52-72`), order validation (`orders.ts`), and the date helpers (`time.ts`).
- **Fix:** Start with the sign-up hook and `orderInput`. A handful of cases each is enough.

#### 🔵 Low — Unused scaffold files
- **Where:** `public/file.svg`, `globe.svg`, `next.svg`, `vercel.svg`, `window.svg` (no references in `src/`); `src/components/ui/` — `alert-dialog`, `badge`, `card`, `checkbox`, `dialog`, `select`, `separator`, `switch`, `table`, `tabs` (imported nowhere outside `ui/`)
- **Why it matters:** Dead weight and extra surface to keep updated. The five SVGs are leftovers from the Next.js starter.
- **Fix:** Delete the SVGs. Remove the unused UI components, or leave them if you expect to use them soon. They can be re-added with the shadcn CLI.

#### ⚪ Info — Small housekeeping
- `cn` is imported from `"cn"` in `components/ui/*` and from `@/lib/utils` (which re-exports it) in the pages. Both work; pick one.
- `pnpm outdated`: `react`/`react-dom` have a patch release (19.3.1). The dev tools (`eslint` 10, `typescript` 7, `@types/node` 26) are major jumps, not urgent.
- No `TODO`/`FIXME`/`HACK` markers, no `console.*` outside the seed script, no empty `catch` blocks except the two deliberate fail-closed ones (`settings/export/route.ts:10`, `system-status.ts:26`).

### Findings

#### 🟡 Medium — The privacy page ships with a yellow "Needs your details" marker
- **Where:** `src/lib/legal.ts:5` (`contactEmail: null`), `src/app/(legal)/privacy/page.tsx:71`, `src/components/legal-blank.tsx`
- **Issue:** The "Questions" section on `/privacy` shows a highlighted "Needs your details: set `contactEmail` in `src/lib/legal.ts`" instead of an address. This is the deliberate "never publish a blank" design, and it works, but today the page staff are pointed to has a gap in it.
- **Fix:** Set `contactEmail` to a made-up address for the demo, or a real one for real use.

#### 🟡 Medium (Potential) — An expired session throws instead of keeping what the person typed
- **Where:** `src/app/(app)/orders/actions.ts:33,63`, `src/lib/auth-guards.ts:21-25`; `src/app` has no `error.tsx`, `global-error.tsx` or `loading.tsx` (0 found)
- **Issue:** If the session ends while someone has the order form open (signed out from another device, or cleared), submitting calls `requireUserAction()`, which throws `Error("Not signed in")`. With no error boundary, they get Next.js's default error screen and the order they were typing is gone. The same applies to any unexpected server error, such as a locked database file.
- **Why it matters:** The order form is used while on the phone with a customer. Losing a half-entered order is the worst place to fail.
- **Not verified:** I read the throw path but did not reproduce it, so the exact screen is unconfirmed.
- **Fix:** Have `saveOrder` return a form error ("You've been signed out. Sign in again; your answers are kept below.") instead of throwing, and add an `error.tsx` at `src/app/(app)/` with a plain message and a way back.

#### 🔵 Low — The privacy page can't be reached from inside the app
- **Where:** only link is `src/app/(auth)/sign-in/page.tsx:20`; the page's only way out is "Back to sign in" (`(legal)/layout.tsx:11`)
- **Issue:** Once signed in, nothing in the header, the settings pages or the help guide links to "What this stores". A signed-in person who opens it by address sees "Back to sign in" rather than a way back to their orders.
- **Fix:** Link it from the You settings page, and make the legal layout's back link go to `/` when there is a session.

#### 🔵 Low — Sign-in and sign-up pages don't send a signed-in person onward
- **Where:** `src/app/(auth)/sign-in/page.tsx`, `(auth)/sign-up/page.tsx` (no session check)
- **Issue:** Someone already signed in who opens `/sign-in` sees the form again.
- **Fix:** Call `getSession()` in the page and `redirect("/")` when there is one.

#### 🔵 Low — The main and settings menus don't show which page you're on
- **Where:** `src/app/(app)/layout.tsx:28-38`, `src/app/(app)/settings/layout.tsx:11-27`
- **Issue:** The links are styled the same whether current or not, and have no `aria-current`. The status filter on All orders does it properly (`orders/page.tsx:69`), so the pattern already exists.
- **Fix:** A small client component for the nav links using `usePathname()`.

#### 🔵 Low — Small accessibility gaps
- **Where:** `src/components/order-form.tsx:24-31`; `src/app/(app)/layout.tsx`
- **Issue:** Field errors use `role="alert"` (good) but are not linked to their inputs with `aria-describedby`, and the inputs don't get `aria-invalid`. There is no "skip to content" link. Every form control has a `<label>`, icon buttons have `aria-label`, `<html lang="en">` is set, and tap targets in the order form are 44px (`h-11`).
- **Fix:** Add `aria-invalid` and `aria-describedby` to the order form fields; add a skip link in the app layout.

**Checked and fine:** empty states exist for Coming up, All orders (with and without a filter), the activity list, and the devices list (loading and error text too). The viewport and dynamic-height handling use `100dvh` and the Next default viewport meta. Overdue orders have their own section so they can't be missed. Cancel and example-removal both ask for confirmation.

**Needs a live run to confirm (not checked):** colour contrast of the muted text on the paper background, real layout at phone widths (the 3.25rem day column and the wrapping header), keyboard focus order through the help sheet, and browser console errors.
